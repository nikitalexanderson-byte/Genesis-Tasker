## Цель и критерий полноценного E2EE

Сервер GENESIS не должен получать или самостоятельно восстанавливать новые пользовательские root/DEK и приватное содержимое. Наличие AES-GCM при серверном хранении открываемого ключа не считается выполнением.

Полный охват: личные проекты, задачи внутри GENESIS, привычки и трекеры, ФЮЗИС, дневники, заметки, майндмепы, приватные данные Авроры/Стойхейона, соответствующие документы, вложения и previews, локальные очереди/черновики, личные архивы, а также содержимое общих проектов для участников. Состав уточни по реальному коду; не исключай незаметно обнаруженные категории.

Google Tasks/Calendar, явно выбранная внешняя обработка, identity, billing, ACL, квоты и необходимые технические метаданные имеют отдельные границы. Нельзя сохранить передачу читаемого текста Google и обещать недоступность этого текста Google/backend. Создай ясное разделение приватной записи GENESIS и её внешней копии. Не удаляй старые Google-данные и не отключай интеграции молча.

Общий user ID неизменен. Google-вход аутентифицирует пользователя, но на новом устройстве не расшифровывает vault автоматически. Администратор может восстановить identity по процедуре; он не получает возможность открыть E2EE-данные.

Раздели:

## Этап 3 Ключи и клиентский vault

Создай случайный 256-битный root новой эпохи на клиенте. Ключи данных разделяй по назначению. Не выводи root из Google identity, токена, email или серверного секрета.

Ключи каждой эпохи должны быть неизвестны серверу. Запрети raw key в API, логах, analytics, crash reports и административных функциях. Для мигрированного scope не допускай возврата keyMode в account и вызова legacy wrapWorkspaceKey.

Каждое устройство имеет отдельные ключи подписи и получения envelopes. Разрешённость нового устройства подтверждается уже доверенным устройством либо независимой recovery authority. Серверный boolean не является криптографическим подтверждением.

Recovery secret генерируется заново из 32 случайных байт и хранится пользователем отдельно. Не переиспользуй старый recoveryCode, который сохранялся вместе с ключом в localStorage. Recovery secret не выдаёт серверную сессию и не переносит entitlement.

Если нужна парольная обёртка, используй проверенный Argon2id с измеренными параметрами, нижними и верхними лимитами. Не применяй пароль Google. У высокоэнтропийного recovery secret свой derivation с domain separation.

Для устройства реализуй enrollment с одноразовым challenge, привязкой к user ID, ключу, сессии и сроку, QR/fingerprint и подписью. Проверь подмену ключа, replay, чужой аккаунт и отмену. Подписывай изменения device directory и храни checkpoints.

Отзыв устройства закрывает сессии и право новых записей, меняет security epoch и независимые ключи будущих данных. Новый root не оборачивается старым, доступным отозванному устройству. Известные ему старые данные невозможно отозвать задним числом.

Web хранит зашифрованные IndexedDB/cache/outbox/drafts; root в памяти активной разблокированной сессии. Не заменяй raw localStorage key тем же raw key в IndexedDB. Для повторной разблокировки используй проверенный пользовательский секрет или платформенный механизм с поддержанным fallback; не обещай защиту от same-origin XSS только из-за extractable=false.

Android сохраняет field encryption/Keystore и добавляет защиту новых ключей/очередей. Зафиксируй поведение biometric/device credential, блокировки, background workers и инвалидирования ключа. Ошибка Keystore не приводит к созданию пустой БД.

## Этап 4 Формат и серверный контракт

Реализуй versioned AEAD envelope: owner/project, domain, object ID, schemaVersion, cryptoEpoch, key ID, revision и device ID связаны AAD. Контекст вычисляется одинаково в JS/Kotlin и сравнивается с ожидаемым получателем/объектом.

Для AES-GCM используй строгие nonce/tag lengths и доказуемую дисциплину уникальности nonce в заданных лимитах. Retry передаёт тот же ciphertext, а не повторно шифрует другой plaintext тем же nonce. Защити restore, multi-device concurrency и clone state.

Для файлов: отдельный file key, проверенная схема chunks, привязка позиции/размера/контекста, итоговый аутентифицированный manifest; не выдавай усечённый файл за успешный.

Подписывай авторизованным device key заголовок и hash ciphertext. Backend проверяет owner/ACL, подпись, epoch, обязательный expectedRevision, idempotencyKey и размеры. Повтор одного ID с другим payload — ошибка. Ввод в парсеры и KDF ограничен по ресурсам.

Идентификаторы и технические метаданные могут быть открыты; названия, заметки, значения трекеров, имена файлов и plaintext hashes не публикуй в AAD или телеметрии.

Введи единый middleware/policy для всех изменяющих маршрутов. После activation старые workspace/key/envelope, shared, private-doc и restore-пути не должны обходить новый контракт.

Сервер не может проверить смысл plaintext: полноту миграции подтверждают клиенты и manifest. В ответах различай upgrade required, unlock required, stale epoch, revoked device, conflict и corruption. Никаких silent plaintext fallback, автоматической очистки или downgrade.

Для antirollback используй доверенные checkpoints. Не обещай, что один AAD или серверный счётчик обнаружит полный откат сервера для совершенно нового устройства. Для защиты от fork нужна внешняя опора/сверка доверенных устройств; отрази фактически реализованную гарантию.

## Этап 5 Безопасная миграция

Реализуй идемпотентную state machine по каждому scope:

legacy → preparing → uploading → verified → active → retirement.

До первого сетевого sync создай защищённый snapshot локальных данных, outbox, черновиков, tombstones и нужной metadata. Нельзя сначала скачать серверное состояние поверх локального и только потом сохранять резерв.

Migration session содержит migrationId, source revision/generation, lease/fence, целевую эпоху и checkpoint. После snapshot сведи legacy server state и локальные изменения по правилам конфликтов. Изменения во время переноса остаются в защищённой очереди.

Сгенерируй новые независимые root/DEK и перешифруй все данные и дочерние ключи, которые раскрывались через старый root. Одного rewrap прежнего server-known DEK недостаточно.

Загружай shadow generation, не удаляя действующую. Проверяй повторным скачиванием и расшифровкой manifest, полноту объектов/файлов/очереди, дубли, tombstones. Проверяй recovery unwrap и второй клиент, где он доступен.

Финальный commit по CAS переключает активное поколение, ключевую эпоху и запрет legacy writes атомарно. При конфликте повтори сведение. До commit отмена безопасно оставляет legacy; после commit возврат к серверно читаемому формату запрещён.

Офлайн-устройство после обновления самостоятельно открывает прежнюю локальную базу, делает snapshot, получает доступ к новому vault и преобразует старый outbox. Не требуй, чтобы оно успело установить 3.3.5. Не воскрешай удалённые записи без разрешения конфликта.

Старые server keys/copies удаляй только по отдельному утверждённому плану retention с учётом системных/offsite backups. Не обещай, что новая схема защитила уже украденную историю. До удаления сохранены проверенные способы восстановления.

Backup import не возвращает права на подписку, payments, account sessions, Google tokens, device approvals и shared ACL. Старый архив преобразуется на клиенте в актуальное поколение.

Update discovery доступен без активной account session. Отсутствие сети или ошибка проверки не снимает уже известный обязательный запрет. Зафиксируй поведение первого офлайн-запуска, истёкшей policy и неверных часов; невозможно узнать новую серверную policy на устройстве, которое не выходило в сеть.

Сохраняй все local vault/outbox/drafts. Предусмотри изолированные «Повторить», открытие магазина/разрешённого APK-канала, поддержку и encrypted emergency export, который не включает старые рабочие функции и sync. Не предлагай удалить приложение ради обновления.

Проверь фактическую совместимость certificate/lineage Play и сайта-APK. Не считать SHA256 на том же сервере независимой подписью; сохраняй штатную проверку package/signature Android. При несовместимости не делай destructive reinstall.

При ошибке доставки новой версии не ослабляй crypto protocol мигрированного аккаунта. Диагностируй канал и исправляй доступность. Перед активацией порога должен существовать проверенный путь обновления.

Серверный version header не является защитой. Проверять нужно crypto format, epoch, подпись и право устройства; устаревшая 3.3.4 может не показать новый gate, но не должна писать в активный E2EE scope.

## Этап 8 Android 3.3.6

Реализуй тот же crypto contract, vault, enrollment, recovery, imports и migration state machine в native-клиенте. Примеры JS/Kotlin должны совпадать побайтово.

Прямые обновления 3.3.4 → 3.3.6 и поддерживаемых старых установок → 3.3.6 обязательны. Play может пропустить 3.3.5. Проверяй migrations всех локальных schemaVersion и сохранение data/outbox.

Полный private-content coverage включает общие проекты и вложения. Если какое-то направление не готово, не объявляй 3.3.6 завершённым переходом «всего» на E2EE.

Существующие E2EE-сообщения сохранить читаемыми. Решение по ratchet/forward secrecy принимай отдельным ADR с готовой библиотекой; при сохранении прежней схемы честно укажи её ограничение, не ломая историю.

Новая версия может предлагать пользователю подготовку recovery и migration, но ошибка или отказ на этапе сохранения recovery не должна уничтожать данные. После активированного crypto cutover старый sync не включается; доступны безопасное завершение/восстановление и поддержка.

Не фиксируй updater навечно на строке 3.3.6. Более новая совместимая версия должна удовлетворять policy и самостоятельно мигрировать старое хранилище.

## Проверки и доказательства

Выполни 48 сценариев отчёта в реально затронутом объёме. Минимальные обязательные группы:

1. Межплатформенные vectors, tamper/AAD, malformed envelopes, nonce/retry, files/chunks.
2. Отсутствие новых raw keys/plaintext в server DB/config/logs, network traces, browser storage и Android temp/backup.
3. Enrollment MITM/replay, отзыв устройств и участников, ротация будущих ключей, recovery на чистом клиенте.
4. Снимок до сети, crashes на каждой стадии, параллельная миграция, CAS/idempotency, offline outbox, tombstones, legacy writes после activation.
5. Прямые обновления старых версий, signature/package/versionCode и сохранение реальных данных.
6. Play cancel/error/resume/process death/no network/no space/no Play, неподходящий rollout/channel, gate через все entrypoints.
7. Архивы разных поколений, неподдельность прав billing/ACL/identity, восстановление системной копии.
8. 14 языков с смысловой вычиткой, особенно английского: update/recovery/privacy/loss of keys. Проверка ключей не заменяет вычитку.
9. Web 360/390/768/1440 в обеих схемах, font scale, accessibility, native API 26+ и реальные разрешённые устройства.

Существующие 22 JS-теста и 9 backend suites из аудита — исходная точка, не доказательство новой реализации. Повторяй нужные suites после изменения их области; не заменяй сценарии потери данных тестами, повторяющими строку реализации.

Криптографические и парсерные тесты используют синтетические данные; production account/config/DB не трогай для тестирования. Android-сборки и установки выполняй только в пределах актуальных разрешений, отдельный test package не удаляет основное приложение.

На каждом этапе сохраняй commit, команды, exit status, результаты, допустимые traces и фактически непроверенные состояния. Не печатай секреты, личный контент и реальные recovery codes.

## Порядок включения и публикации

Отдельно подготовь к проверке:

1. ADR, реестр данных, baseline и hardening.
2. Совместимые backend formats/policy и web implementation за флагами.
3. Web pilot и проверяемая миграция.
4. Android 3.3.5 bridge.
5. Android 3.3.6, прямые migrations и полный coverage.
6. Пакет релизной проверки и runbook activation/retirement.

Публикации выполняются только по актуальному прямому поручению. Перед запросом на публикацию уже должны быть конкретные готовые результаты и доказательства, а не предложение начать анализ.

Для обязательного update floor сначала должны быть подтверждены доставка совместимого выпуска нужной аудитории, обновление поверх существующей подписи, свободный путь recovery и отсутствие critical data-loss дефектов. Потом включается policy и account/scope crypto enforcement.

После crypto cutover допустим только откат на совместимую E2EE-реализацию. Автоматический DB rollback, возврат account-key mode или очистка local storage запрещены. При аварии блокировать опасные записи, сохранять ciphertext и исправлять совместимым выпуском.

Обнови документацию приватности и внешних обработок, release notes, support runbook, Play Data safety в затронутом объёме и 14 локализаций. Не обещай отсутствие metadata, невозможность доступа с заражённого разблокированного устройства, абсолютную защиту web от подмены origin или мгновенное обновление всех пользователей Play.

# Portable v1 backup authenticated-header compatibility

20 November 2026. This is the existing independent-key `.genesisbackup` format,
not a new E2EE envelope suite or permission to activate account migration.

Android's platform `JSONArray.toString()` escapes `/` as `\/`. JavaScript's
`JSON.stringify()` leaves it literal. The v1 backup header authenticates the
wrapped AES key, whose standard Base64 can contain `/`. Consequently native and
web implementations could authenticate different bytes for the same semantic
header. JVM org.json does not reproduce the actual Android quoting behavior;
the old JVM roundtrip alone could not detect this interoperability problem.

The large API26 attempt03 rejected its generated file with the existing
key/integrity error, while API34 passed. Its original generated file was removed
by the test's normal cleanup, so the precise wrapped-key bytes from that failure
are not claimed as retained evidence. The platform quoting difference was then
observed in the actual API26 source fixture and independently reproduced with
fixed cryptographic vectors that deliberately contain a solidus in the wrapped
key. The initial common-reader regression passed2/3: the historical Android
encoding failed authentication. After the change all8 selected format/portability
tests pass; full JS is1814/1814,0 fail/skip.

## Contract

New writers on both platforms always authenticate the compact JavaScript encoding:
`["genesisbackup",1,backupId,"A256GCM+A256KW",wrappedKey]`.
Native code validates the dynamic UUID and canonical40-byte wrapped-key Base64
before constructing these ASCII bytes; platform-specific JSON quoting cannot
change them. The large fixture now forces a solidus and uses this same writer
contract, so a lucky random key cannot hide the mismatch again.

Readers retain exactly two authenticated encodings of this same legacy v1 header:
canonical JSON, followed only after tag failure by the historical Android
solidus-escaped representation when they differ. AES-KW unwrap, nonce/tag sizes,
ciphertext limits, digest checks, all semantic header fields and owner/payload
validation still apply. The second attempt does not omit or substitute context,
accept plaintext, change algorithm, recover a missing key or execute restore.
An unknown schema/suite or malformed wrapped key is not another trial mode.
Both attempts remain entirely on the user's device.

## Evidence and acceptance limits

generated by `scripts/qa/backup-portability-vectors.mjs`. Its known test key is
never appropriate for user data. The two encryptions have distinct fixed nonces.
The independent vectors use WebCrypto directly instead of the product's header
helper. Tests require successful authentication of both histories and rejection
of changed header, wrapped key, recovery key and modified ciphertext even after
its unkeyed digest is recomputed. A separate decrypt checks that new writers use
canonical bytes, so compatibility read attempts cannot hide writer drift.
